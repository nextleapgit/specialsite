# معايير الفرونت إند — React وتجربة المستخدم

ابنِ واجهة جذابة ومتجاوبة وقابلة للوصول، متصلة بعقد API حقيقي. اقرأ تعليمات المستودع ونظام التصميم والحزم أولًا. احترم نطاق الطلب؛ لا تفرض إعادة تصميم أو تغيير router أو ترقية شاملة على إصلاح محدود. اشرح العمل للمستخدم بالعربية، واستخدم الإنجليزية لأسماء الكود.

## سياسة الاعتماديات والتصميم المملوك للمشروع

- لا تستخدم مكتبات أو إضافات أو قوالب أو خطوطًا أو أيقونات تتطلب شراءً أو اشتراكًا أو ترخيص إنتاج مدفوعًا. لا تعتمد على trial أو خطة مجانية محدودة لخدمة مدفوعة كأساس معماري.
- React وTypeScript والأدوات المجانية مفتوحة المصدر مسموحة بعد التحقق من ترخيص الإصدار والأصول واعتمادياتها وملاءمة الاستخدام والتوزيع. حافظ على attribution وإشعارات الترخيص اللازمة.
- اكتب بنفسك layouts وصفحات الحسابات ومكونات المنتج وحالاتها والتفاعلات الخاصة به بدل شراء UI kit أو blocks. استخدم احتياج المنتج والمواصفات العامة، ولا تنسخ مصدرًا مدفوعًا أو تعيد إنتاجه من تسريب.
- يمكن استخدام shadcn/ui المجانية ككود مكونات داخل المشروع، مع primitives مجانية ومتوافقة من منظومة واحدة. نسخها المرخّص يظل اعتمادًا يحتاج متابعة تحديثات؛ لا تصفه بأنه مكتوب كله من الصفر. لا تستخدم إضافات مدفوعة تشترك معها في الاسم.
- لا تعِد كتابة focus management أو ARIA المعقدة دون حاجة عندما تتوفر primitive مجانية مناسبة. اكتب تنسيق المنتج وتجربته بنفسك، واستخدم قدرات المتصفح والحلول المجانية الموثوقة حيث تقلل الأخطاء.
- إذا كانت ميزة موجودة في مكتبة مدفوعة فقط، نفّذ الحد المطلوب منها بكود المشروع واختبره، دون محاولة بناء إطار عام بديل. لا تستخدم إصدارًا قديمًا غير آمن للاحتفاظ بترخيص مجاني.

## اختيار التقنيات والإصدارات

- الافتراضي لتطبيق حسابات ولوحة تحكم تتصل بباك إند .NET مستقل: React + TypeScript strict + Vite.
- تحقّق من أحدث إصدارات مستقرة متوافقة من المصادر الرسمية عند بدء المشروع. تاريخ صياغة هذه المهارة 2026-09-14؛ لا تتعامل مع أرقام الإصدارات الواردة في محادثات قديمة على أنها أحدث الإصدارات دائمًا.
- استبعد canary وbeta وRC افتراضيًا. افحص peerDependencies وتوافق React وTypeScript وأداة البناء. إذا تعذر التحقق من الأحدث، اذكر ذلك واستخدم النسخة المتحققة المناسبة للمشروع.
- استخدم Node.js مدعومًا ومتوافقًا مع أداة البناء، ومدير الحزم الموجود في المستودع. ثبّت الإصدارات وملف قفل واحد، واستعمل التثبيت المقفل في CI.
- فضّل TanStack Router للتوجيه المكتوب الأنواع وTanStack Query لحالة الخادم في المشروع الجديد. احترم React Router أو غيره إن كان معتمدًا بالفعل؛ لا تضف مكتبتين لحل المسؤولية نفسها.
- استخدم React Hook Form وZod للنماذج المركبة، وTailwind CSS مع مكونات مجانية قابلة للتخصيص للتصميم. لا تُلزم نموذجًا تافهًا بطبقات غير لازمة.
- احتفظ بحالة العرض الصغيرة محليًا في React، وبحالة URL القابلة للمشاركة في search params. لا تضف Redux أو مخزنًا عامًا لمجرد الاحتفاظ بالمستخدم أو نسخ بيانات Query.
- اختر Next.js أو إطار عرض خادمي عندما تبرر متطلبات الصفحات العامة وSEO وSSR تشغيله. لا تضف خادم JavaScript ثانيًا افتراضيًا إلى تطبيق له باك إند .NET؛ وثّق الحدود إذا دعت الحاجة.

## تنظيم الكود

- نظّم حسب الميزة: auth وaccount وsessions وadmin عند الحاجة، مع app للمزودين والتوجيه، وcomponents/ui للعناصر العامة، وlib/api للاتصال، وlocales للترجمة. لا تنشئ مجلدات فارغة لميزات غير مطلوبة.
- افصل طلبات الشبكة عن مكونات العرض. اجمع تعريفات queries وmutations ومفاتيح cache مع الميزة ذات الصلة، واجعل واجهة المكوّن واضحة بالأنواع.
- استخدم typed client مشتقًا من OpenAPI بأداة مجانية مناسبة أو مكتوبًا يدويًا بعقود صريحة. لا تخمّن endpoints أو تغيّر أسماء الحقول بمعزل عن الباك إند.
- استخدم تحويلات صريحة صغيرة عند اختلاف نموذج العرض عن DTO. لا تضف abstraction عام أو مكتبة Mapping لمجرد هذا الاختلاف.
- اجعل المكونات المشتركة صغيرة ومحددة المسؤولية. لا تنشئ مكوّن Form أو Table شاملًا لكل الحالات قبل وجود استخدامات تثبت الحاجة.

## عقد API والمصادقة

- اتفق مع الباك إند على المسارات والطرق وDTOs وحالات HTTP وProblemDetails وcode وtraceId وأخطاء الحقول والتصفح والتواريخ والقيم nullable.
- الافتراضي للمتصفح: كوكي مصادقة HttpOnly وSecure يصدرها باك إند .NET، مع origin موحد و/api عند ملاءمة التشغيل. اضبط credentials بحسب النشر، وأرسل رمز CSRF بالطريقة المتفق عليها في الطلبات التي تغيّر الحالة، بما فيها الدخول والخروج.
- لا تحفظ access/refresh tokens أو session identifiers في localStorage أو sessionStorage أو IndexedDB أو مخزن حالة قابل للاستمرار. تفضيلات اللغة والمظهر غير الحساسة يمكن حفظها محليًا.
- كوكي المصادقة HttpOnly لا تقرؤها JavaScript. وجود رمز CSRF منفصل قابل للقراءة حسب تصميم الخادم لا يحوّله إلى كوكي مصادقة؛ لا تخلط الآليتين.
- استخرج المستخدم الحالي وحالة الجلسة من endpoint موثق. حماية المسارات وإخفاء العناصر لتحسين التجربة؛ يجب على الخادم التحقق من الصلاحيات وملكية الموارد.
- عند 401، تعامل مع انتهاء الجلسة بوضوح دون حلقة retries أو redirects. عند 403، اعرض عدم السماح. اسمح بـreturn URL داخلي موثوق فقط، ولا تمرر redirect عشوائيًا من query string.
- عند logout أو تبديل الحساب، ألغِ الطلبات ذات الصلة وامسح cache الحساس، وامنع وصول استجابة قديمة إلى واجهة المستخدم الجديد. طبّق انتهاء الجلسة عبر التبويبات دون مشاركة أسرار.
- إن كان الدخول عبر OIDC/BFF، اتبع redirects وعقد الخادم؛ لا تجمع كلمة مرور مزود خارجي داخل واجهة التطبيق. لا تنفذ OAuth أو WebAuthn تشفيريًا بنفسك.
- لا تُدخل كلمات المرور أو OTP أو رموز الاستعادة أو محتويات الروابط الحساسة في analytics أو logs أو cache. امنع التسرب عبر referrer والمحتوى الخارجي في صفحات الاستعادة، وأزل بيانات الرابط الحساسة بعد التقاطها عندما يسمح التدفق.
- كل إعداد VITE_* يصل للعميل ويمكن كشفه. احتفظ بأسرار البريد ومفاتيح المزودين والتوقيع على الخادم.
- استخدم escaping الافتراضي في React. إذا احتاج المنتج HTML غير موثوق، استخدم sanitizer مجانيًا موثوقًا وسياسة محددة؛ لا تعرضه مباشرة عبر dangerouslySetInnerHTML.

## صفحات الحسابات وتجربة التدفق

- نفّذ فقط الصفحات المطلوبة، مع استيعاب تدفقات التسجيل، تأكيد البريد، إعادة الإرسال، الدخول، نسيان كلمة المرور وإعادة تعيينها، والملف الشخصي والأمان والجلسات عندما تكون ضمن النطاق.
- اجعل رسائل التسجيل والاستعادة متوافقة مع سياسة الخادم لمنع كشف وجود البريد. لا تُظهر للمستخدم تفاصيل أخطاء أمنية داخلية.
- فرّق بوضوح بين انتهاء رابط التحقق وانقطاع الشبكة وفشل الإدخال وانتهاء الجلسة. قدّم إجراءً مناسبًا لكل حالة مثل إعادة الإرسال أو العودة للدخول.
- لا تعرض نجاحًا قبل قبول الخادم للعملية. امنع الإرسال المتكرر أثناء التنفيذ، لكن احتفظ برسائل الخطأ والحقول غير الحساسة اللازمة للتصحيح.
- عند MFA، لا تعتبر الاستجابة التي تطلب العامل الثاني دخولًا مكتملًا. عالج TOTP ورموز الاسترداد كخطوة مستقلة، واطلب إعادة التحقق للعمليات الحساسة وفق عقد الخادم.
- عند Passkeys، استخدم WebAuthn وقدرات المتصفح مع endpoints موثقة من الباك إند. تعامل مع عدم الدعم وإلغاء المستخدم والمهلة، وقدّم وسيلة بديلة متاحة دون ادعاء نجاح تسجيل المفتاح قبل تأكيد الخادم.
- عند عرض الأجهزة، اشرح أن الأسماء مستنتجة من معلومات العميل وقد لا تكون دقيقة. لا تدّع معرفة الجهاز الفعلي أو موقعه الدقيق؛ اعرض آخر نشاط والجلسة الحالية وإجراءات الإبطال التي يوفرها الخادم.
- اسمح باللصق ومديري كلمات المرور وملء OTP التلقائي. استخدم autocomplete الصحيح مثل email وcurrent-password وnew-password وone-time-code، ولا تعطل هذه الأدوات.

## الاتجاه البصري الافتراضي

- ابنِ هوية بصرية مخصصة ومتسقة. نقطة بداية عند غياب هوية محددة: خلفيات محايدة، لون أساسي نيلي، تدرجات هادئة، مساحات واسعة، تسلسل طباعي واضح، وحدود وظلال خفيفة. غيّرها إذا تعارضت مع العلامة أو طلب المستخدم.
- عرّف design tokens للألوان والخطوط والمسافات والحواف والظلال وحالات التركيز. اجعل الوضع الداكن تصميمًا متزنًا مع تباين مناسب، وليس قلبًا آليًا للألوان.
- على الشاشات الواسعة، يمكن أن تجمع صفحة الدخول نموذجًا مركزًا ومساحة بصرية جانبية. على الهاتف، استخدم عمودًا واحدًا يقدم المهمة الأساسية. لا تجعل الزينة تؤخر الوصول إلى النموذج أو تطغى عليه.
- صمّم بطاقات واضحة للملف والأمان والجلسات، وأزرارًا أساسية وثانوية يسهل تمييزها. اجعل التحميل والنجاح والخطأ والحالة الفارغة جزءًا من التصميم نفسه.
- استخدم خطوطًا عربية/لاتينية مجانية ومرخصة، واستضف الأصول محليًا عند ملاءمة التشغيل. لا تضف صورًا أو خطوطًا أو نصوصًا تجريبية غير مرتبطة بالمنتج لمجرد ملء المساحة.
- استخدم حركة CSS خفيفة لها غرض؛ احترم prefers-reduced-motion. لا تضف مكتبة حركة لانتقال يمكن تنفيذه ببساطة في CSS.

## العربية والوصول والاستجابة

- العربية وRTL افتراضيان لهذا المستخدم في المشروع الجديد ما لم يحدد خلاف ذلك. اجعل النصوص قابلة للترجمة، ودعم الإنجليزية وLTR متسقًا عند إدراجهما في النطاق.
- استخدم lang وdir وخصائص CSS المنطقية مثل margin-inline وpadding-inline وtext-align:start. اضبط اتجاه البريد والأرقام والرموز المعروضة عند الحاجة دون قلب الصفحة أو الأيقونات غير الاتجاهية عشوائيًا.
- استعمل HTML دلاليًا، وتسميات مرتبطة بالحقول، وأخطاء مرتبطة بـaria-describedby، وتنقل لوحة مفاتيح ومؤشر تركيز واضحين. لا تعتمد على اللون وحده لشرح النجاح أو الخطأ.
- في dialogs، اضبط حصر التركيز واستعادته والإغلاق المناسب. أعلن تحديثات الحالة لقارئات الشاشة دون تكرار مزعج. استهدف WCAG 2.2 AA، ولا تدّع الامتثال الكامل من فحص آلي وحده.
- اختبر النص العربي الطويل والتكبير والتفاف الأزرار، وأحجام الهاتف واللوحي والحاسوب. امنع التمرير الأفقي غير المقصود وتداخل العناصر مع لوحة مفاتيح الهاتف.

## البيانات والأداء والتحقق

- عيّن سياسة staleTime وrefetch وretry حسب البيانات. لا تكرر تلقائيًا طلبات الدخول أو إرسال البريد أو العمليات الحساسة على نحو يكرر أثرها. تعامل مع 429 وRetry-After دون تخمين مهلة مختلفة عن الخادم.
- استخدم إلغاء الطلبات وquery keys المعزولة بالمستخدم/المستأجر حيث يلزم. لا تحفظ cache حسابات حساسًا على القرص افتراضيًا. عالج سباق الطلبات أثناء تغيير المستخدم أو الفلاتر.
- استخدم code splitting للمسارات الثقيلة، وحمّل الأصول بحسب الحاجة. قيّم الأداء فعليًا قبل إضافة memoization أو تحسينات غير مبررة.
- اختبر المكونات ذات السلوك المهم بأدوات مجانية مناسبة مثل Testing Library وVitest، واختبر الرحلات الحرجة بـPlaywright عند تنفيذها. تجنّب الاختبارات التي تطابق تفاصيل implementation أو شكل DOM بلا قيمة سلوكية.
- شغّل typecheck وlint وproduction build والاختبارات المناسبة. راجع بصريًا حالات التحميل والخطأ والنجاح والوضع الداكن وRTL والشاشات المستهدفة بأدوات المعاينة المتاحة.
- افحص لوحة المفاتيح والتركيز والتباين، وصحة الاتصال الفعلي بالـAPI. ميّز في التسليم بين اختبار mock واختبار تكامل حقيقي، وبين لقطة شكلية واختبار سلوك.
- إن لم يتوفر الباك إند أثناء بناء الواجهة، استخدم mock واضحًا محصورًا في التطوير واذكر الوظائف غير المتصلة. لا تُظهر تدفق مصادقة تجريبيًا على أنه نظام إنتاج مكتمل.
- سلّم الواجهة وعقودها ونتائج التحقق الفعلية وأي قيود باقية. لا تنشر الموقع أو تغيّر إعدادات خدمة خارجية لمجرد تطبيق هذه المهارة؛ اتبع نطاق طلب المستخدم.
