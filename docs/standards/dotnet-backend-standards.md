# معايير الباك إند — .NET وPostgreSQL

طبّق هذه التفضيلات عند إنشاء باك إند جديد أو تعديل ميزة ضمن مشروع .NET. اقرأ تعليمات المستودع وبنيته واعتمادياته أولًا. التغييرات المطلوبة هي نطاق العمل؛ لا تحوّل إصلاحًا محدودًا إلى ترقية شاملة أو إعادة بناء. اشرح القرارات للمستخدم بالعربية، واستخدم الإنجليزية لأسماء الكود والعقود.

## سياسة الاعتماديات وكتابة الحلول

- لا تضف مكتبة أو مكوّنًا يتطلب شراءً أو اشتراكًا أو ترخيص إنتاج مدفوعًا، ولا تعتمد على تجربة مجانية أو حد مجاني لخدمة مدفوعة كأساس للحل. لا تنشئ اشتراكات أو موارد مدفوعة دون طلب المستخدم.
- المكتبات المجانية مفتوحة المصدر مسموحة بعد التحقق من ترخيص الإصدار المختار وملاءمته للاستخدام والتوزيع المقصودين. افحص الاعتماديات الانتقالية والإضافات المطلوبة، وسجّل النتيجة باختصار في توثيق الاعتماديات الموجود بالمشروع. حافظ على إشعارات الترخيص الواجبة.
- اكتب البديل المحدود الذي يحتاجه المشروع بنفسك بدل المكوّن المدفوع: معالجات حالات الاستخدام، تحويل DTOs، قواعد العمل، تغليف النتائج، سجل التدقيق وإدارة الجلسات. استخدم مواصفات عامة ومراجع مجانية؛ لا تنسخ مصدرًا مدفوعًا أو تفك حمايته.
- لا تضف MediatR أو AutoMapper إلى مشروع جديد بهذه التفضيلات. استخدم handlers مسجلة في DI وتحويلات صريحة. لا تبنِ إطار Mediator أو Mapping عامًا لمجرد استبدالهما.
- لا تستخدم إصدارًا قديمًا غير آمن للاحتفاظ بترخيص مجاني. في مشروع قائم، حدّد الاعتماد المتعارض واستبدله ضمن نطاق العمل، مع الحفاظ على السلوك والتحقق منه.
- كتابة الحلول من الصفر تعني منطق التطبيق والتنسيق بين المكونات؛ استخدم تنفيذات .NET المجانية والموثوقة للتشفير، وتجزئة كلمات المرور، والكوكيز، وData Protection والتحقق من البروتوكولات. لا تبتكر خوارزمية تشفير أو بروتوكول دخول.

## الإصدارات والأدوات

- عند مشروع جديد، تحقّق من المصادر الرسمية لأحدث إصدار .NET مستقر طويل الدعم. خط الأساس عند إنشاء هذه المهارة في 2026-09-14 هو .NET/ASP.NET Core 10 وC# 14، وليس تثبيتًا دائمًا لهذا الرقم.
- استخدم EF Core وNpgsql المتوافقين مع إصدار .NET المختار، وPostgreSQL بأحدث إصدار مستقر يدعمه التشغيل الفعلي. لا تفترض أن أرقام التصحيح لجميع الحزم متطابقة.
- استبعد Preview وRC من الاختيار الافتراضي. تحقّق من تاريخ الدعم، والتوافق الفعلي، والترخيص قبل تثبيت أحدث إصدار؛ إذا تعذر التحقق، صرّح بأن الإصدار غير متحقق بدل وصفه بالأحدث.
- ثبّت SDK في global.json، وأدر حزم .NET مركزيًا عبر Directory.Packages.props عندما يناسب الحل، واستعمل قفل استعادة الحزم في CI. لا تستخدم مراجع عائمة أو صور حاويات موسومة latest في إصدار الإنتاج.
- فضّل ASP.NET Core وSystem.Text.Json وDI وLogging وRate Limiting وOpenAPI المدمجة. أضف FluentValidation المجانية عند وجود قواعد تستفيد منها، بدل تكرار نظام تحقق ثانٍ بلا حاجة.

## المعمارية الافتراضية

- ابدأ بتطبيق خلفي واحد مقسّم إلى وحدات وظيفية (Modular Monolith). استخدم حدودًا مثل Accounts وAuthorization وNotifications وAudit عندما يحتاجها النطاق، دون إنشاء وحدات فارغة.
- اجمع ملفات كل حالة استخدام بأسلوب Vertical Slice، مثل Register وResetPassword وRevokeSession. استخدم Clean Architecture لعزل منطق الاستخدام عن HTTP والتخزين والخدمات الخارجية؛ لا تفرض أربع طبقات على كل عملية بسيطة.
- فضّل Minimal APIs بمجموعات مسارات ونقاط نهاية صغيرة في المشروع الجديد. احترم Controllers في المشروع القائم؛ لا تغيّر الأسلوب لمجرد التفضيل.
- اجعل نقطة النهاية مسؤولة عن HTTP وتوجيه الطلب، ومعالج الاستخدام مسؤولًا عن التنسيق، وطبقة البنية التحتية مسؤولة عن التخزين والإرسال. اجعل abstractions محدودة بالحدود التي تحتاج تبديلًا أو عزلًا فعليًا.
- استخدم UserManager وSignInManager لعمليات Identity. افصل نموذج الهوية التقني عن نماذج المجال عندما توجد قواعد أعمال مستقلة، ولا تعِد كيان Identity مباشرة في استجابة API.
- استخدم EF Core مباشرة حيث يكون ذلك واضحًا. لا تضف Generic Repository أو Unit of Work يكرر قدرات DbContext، ولا تشترط قاعدة قراءة مستقلة لتطبيق الفصل المنطقي بين القراءة والكتابة.
- استخدم DDD وDomain Events فقط للقواعد والتفاعلات التي تبررهما. أضف Microservices أو Event Sourcing أو وسيط رسائل خارجي عندما يثبت احتياج النطاق، لا كشرط لجودة الكود.

## REST وعقد الفرونت إند

- صمّم DTOs صريحة وحدودًا لأطوال المدخلات وأحجام القوائم، وامنع mass assignment. لا تثق في userId أو role أو tenantId القادم من العميل لإثبات صلاحية.
- اجعل OpenAPI المرجع المشترك للعقد: المسار، الطريقة، DTOs، أخطاء التحقق، المصادقة، التصفح والتصفية. اتبع سياسة versioning الموجودة، وحدد سياسة واضحة في المشروع الجديد.
- استخدم ProblemDetails مع code ثابت يمكن للواجهة ترجمته، وtraceId، وأخطاء حقول منظمة. حافظ على دلالات status codes؛ لا تحول كل الأخطاء إلى HTTP 200.
- لا تضع عمليات تعديل في GET. استخدم pagination محدودة، وقيودًا على الفلترة والترتيب، وحدود طلبات مناسبة. ميّز بين الطلب غير المصادق 401 والمنع 403.
- استخدم سياسات التفويض داخل الخادم، مع فحص ملكية المورد وحدود المستأجر إن كان النظام متعدد المستأجرين. إخفاء الزر أو حماية مسار React لا يمنحان حماية للـAPI.
- اجعل التواريخ في العقود ISO 8601 واضحة المنطقة الزمنية؛ مثّل لحظات الوقت في PostgreSQL بشكل مناسب مثل timestamptz. اتفق على nullable والـenums والتصفح مع الواجهة قبل تنفيذ طرفي العقد.

## الهوية والجلسات

- لتطبيق ويب مملوك للمستخدم: ASP.NET Core Identity مع PostgreSQL هو الافتراضي. وفّر واجهة React وAPI ببناءين مستقلين، ويمكن نشرهما خلف origin واحد مع /api لتبسيط تشغيل المتصفح.
- استخدم كوكي مصادقة Secure وHttpOnly وسياسة SameSite ملائمة لمسار الدخول. نفّذ حماية CSRF للطلبات التي تغيّر الحالة، بما فيها الدخول والخروج، بحسب آلية المصادقة المستخدمة. لا تعامل SameSite أو CORS كبديل عام لـCSRF.
- إذا تعذر origin موحد، اضبط CORS لأصول محددة والـcredentials وخصائص الكوكي وCSRF بالتناسق، واختبر القيود الفعلية للمتصفحات. لا تستخدم wildcard مع credentialed requests.
- لا تنشئ JWT لأن الواجهة React، ولا تحفظ access/refresh tokens في localStorage أو sessionStorage. رموز Identity API المدمجة ليست JWT ولا خادم OIDC عامًا.
- عند اشتراط SSO أو عملاء مستقلين، استخدم مكوّن بروتوكول مجاني متوافق مثل OpenIddict بعد التحقق من ترخيصه. اكتب تجربة الحسابات بنفسك فوقه؛ لا تعِد تنفيذ OAuth/OIDC. استخدم Authorization Code مع PKCE، وBFF للاحتفاظ بتوكنات المتصفح على الخادم عند ملاءمته. لا تستخدم password grant أو implicit flow كاختيار جديد.
- عند استعمال refresh tokens، طبّق دورة حياة وإبطالًا وكشف إعادة الاستخدام تناسب المزود والتدفق؛ عالج طلبات التجديد المتزامنة. ميّز بين إبطال refresh token وبين انتهاء access token غير المرتبط بفحص خادمي.
- للتسجيل والاستعادة، استخدم مزودي رموز Identity المناسبين، ورسائل عامة لا تكشف وجود البريد، وحدود طلبات حسب الحساب ومصدر الطلب، وصلاحية زمنية محددة. لا تغيّر الحساب بمجرد طلب إعادة التعيين.
- اجعل رمز الاستعادة غير قابل لإعادة الاستخدام بعد نجاح العملية، واختبر ذلك. اضبط روابط العودة على وجهات موثوقة؛ لا تولّد رابط استعادة من Host غير موثوق، ولا تسجّل الرموز في السجلات.
- استخدم PasswordHasher الموثوق وقواعد كلمات مرور ملائمة، ومنع كلمات المرور الشائعة/المخترقة عندما تتوفر آلية مناسبة مجانية. لا تخزن كلمة المرور قابلة للاسترجاع، ولا تستخدم SHA منفردًا لتجزئتها.
- عند MFA: ادعم TOTP ورموز استرداد تستخدم مرة واحدة. احمِ أسرار TOTP المخزنة بتشفير وإدارة مفاتيح ملائمة، واطلب تحققًا حديثًا لتغيير وسائل الحماية. افصل استرداد MFA عن إعادة تعيين كلمة المرور.
- عند Passkeys: استخدم قدرات Identity المتوافقة، وتكامل WebAuthn مع React. تحقّق من challenge قصير العمر وغير قابل لإعادة الاستخدام وorigin وRP ID وسياسة user verification. لا تفترض أن MapIdentityApi ينشئ تجربة React كاملة تلقائيًا.
- إدارة الأجهزة ميزة إضافية: سجل جلسات خادمي قابل للإبطال، مع انتهاء خمول وانتهاء مطلق، وربط الجلسة بالكوكي والتحقق من إبطالها في الطلبات. لا تعتمد على حذف كوكي المتصفح أو Security Stamp دوري وحده لتحقيق إبطال فوري لجلسة مسروقة.
- اطلب إعادة تحقق للعمليات الحساسة، وطبّق سياسة معلنة لإبطال الجلسات عند تغيير/استعادة كلمة المرور أو تعطيل الحساب. لا تربط حساب مزود خارجي تلقائيًا بمجرد تطابق بريد غير موثوق.

## PostgreSQL والتشغيل

- استخدم migrations قابلة للمراجعة، وفهارس وقيود uniqueness على القيم المطبّعة المناسبة. إعداد RequireUniqueEmail في التطبيق لا يغني وحده عن ضمان الاتساق مع التسجيل المتزامن في قاعدة البيانات.
- استخدم معاملات محدودة وتحققًا من التزامن حيث تتنافس العمليات، مع async وCancellationToken. تجنّب N+1 والتحميل غير المحدود، واستعمل projections وAsNoTracking للقراءات المناسبة.
- أرسل البريد عبر واجهة داخلية قابلة للتبديل. التطوير يستخدم صندوق بريد محليًا، والإنتاج يستخدم SMTP أو مزودًا يحدده المستخدم؛ لا تفترض أن توصيل البريد في الإنتاج مجاني لمجرد مجانية المكتبة.
- عندما يلزم ضمان تسجيل مهمة الإرسال مع العملية، استخدم Outbox في PostgreSQL وBackgroundService مجانيًا: retries محدودة، backoff، حجز آمن عند تعدد العمال، ومراقبة للرسائل المتعثرة. توقّع التكرار وصمّم المعالجة وفقه؛ لا تعد بضمان exactly-once.
- احفظ مفاتيح Data Protection بشكل دائم ومشترك بين نسخ التطبيق نفسه مع صلاحيات محدودة وتشفير at rest. حافظ على المفاتيح اللازمة لفك البيانات القديمة، وافصل البيئات والتطبيقات المختلفة.
- استعمل إدارة أسرار مناسبة وHTTPS وإعدادًا موثوقًا للـreverse proxy. استبعد كلمات المرور والتوكنات وأسرار MFA من السجلات والتتبعات.
- اجعل السجلات منظمة ومرتبطة بمعرّف تتبع، وأضف health checks ومقاييس لمشكلات الدخول والإرسال. استخدم OpenTelemetry المجاني عند الحاجة، ولا تشترط منصة مراقبة مدفوعة.
- نفّذ migrations الإنتاج في خطوة نشر مضبوطة بدل تنفيذها تنافسيًا من كل نسخة. حدّد النسخ الاحتياطي واختبار الاستعادة عندما يشمل الطلب تجهيز الإنتاج.

## الاختبار وتسليم العمل

- اختبر قواعد العمل المهمة بوحدات صغيرة، وتدفقات الهوية والتخزين باختبارات تكامل مع PostgreSQL فعلية معزولة، مثل Testcontainers المجانية عند توفر Docker. لا تعتمد على EF InMemory لإثبات سلوك PostgreSQL.
- اختر الحالات المناسبة للتغيير: التسجيل المتزامن، تأكيد البريد، رمز استعادة منتهي أو معاد استخدامه، منع كشف الحساب، CSRF، rate limiting، الملكية، وإبطال الجلسات. اختبر MFA وPasskeys عند تنفيذهما.
- افحص عدم كشف أسرار في الأخطاء والسجلات، وتحقق من عدم إنشاء دخول كامل قبل اكتمال MFA. لا تدّع نجاح اختبار بريد أو مزود خارجي لم يُشغّل.
- شغّل build والاختبارات المطلوبة وفحص الاعتماديات المتاح. سلّم ما تغير، وعقده، وطريقة تشغيله، ونتائج التحقق الفعلية وأي قيود باقية. هذه المهارة ليست إذنًا بنشر الإنتاج أو تعديل خدمات خارج نطاق طلب المستخدم.
